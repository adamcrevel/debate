Goal

A Python engine that runs structured, evidence-grounded debates: a user names a topic (narrow or wide), the engine forms two 3-agent teams (FOR / AGAINST), and feeds them questions one at a time — supplied directly or self-generated in auto mode — through a researched debate pipeline (team huddle, openings, a budgeted rebuttal loop, closings, judge verdict). Every agent turn is a single non-interactive call to the omp CLI, so the engine never talks to a model provider directly and stays provider-agnostic by construction; omp's own web_search tool is how agents ground claims in real evidence. The engine is usable today as an omp skill (CLI + SKILL.md). A Discord bot is explicitly out of scope for this feature — a deliberate follow-up once this engine is proven.

Requirements

  • 1Starting a debate requires a topic (debate start --topic "<text>"); an empty or whitespace-only topic is rejected with a clear error, not silently accepted.
  • 2Starting a debate creates exactly two teams of exactly three agents: FOR and AGAINST, each built from three distinct in-team roles — Lead (delivers openings and closings), Researcher (produces the team's evidence brief), Rebuttal (argues the live rebuttal loop) — one agent instance per role per team, six debater agents total.
  • 3A user can feed a question directly: debate ask "<question text>" runs one full question-debate inside the active debate through the pipeline in Requirement 6.
  • 4debate auto --count N runs N consecutive questions without a human supplying any of them: the engine's own Host agent generates each question from the debate's topic, checked against every question already asked in this debate so it never repeats one, before that question runs through the same pipeline as Requirement 6.
  • 5.claude/skills/debate/SKILL.md documents a second way to drive auto mode: the orchestrating omp session itself composes the next question (using its own judgment, no extra agent call) and passes it to debate ask, as an alternative to delegating question choice to the Host agent in Requirement 4.
  • 6Per question, the engine runs these stages in this exact order: - Huddle (private per team): each team's Researcher agent produces an evidence brief for its team's stance (with --tools=web_search enabled); that brief is included as context in every later prompt to that team's Lead and Rebuttal agents for this question. - Openings: FOR's Lead speaks first, then AGAINST's Lead — one turn each. - Rebuttal loop: AGAINST's Rebuttal agent speaks first, then FOR's, alternating. The loop stops at whichever of two configurable limits is reached first: a maximum number of rebuttal turns (--max-rebuttal-rounds, default 2 rounds = 4 turns — reaching the 4th turn ends the loop after it completes, the 3rd turn does not) or a wall-clock budget for the whole loop (--max-minutes, default 10 — a turn already in flight when the clock expires is still allowed to finish, no new turn starts after). - Closings: AGAINST's Lead speaks first, then FOR's Lead — one turn each, so FOR holds both the opening and the closing word. - Verdict: if the judge is enabled (Requirement 7), one Judge turn; otherwise the question ends after closings.
  • 7A Judge agent — not on either team, --tools=web_search enabled — is on by default. It reviews the full question transcript and produces a verdict naming which side argued the question better, or a declared draw, with a short rationale citing specific turns by stage and side. --no-judge disables Requirement 6's verdict stage entirely for that run.
  • 8Every agent turn (huddle, opening, rebuttal, closing, verdict, and the Host's question generation) is exactly one non-interactive omp -p subprocess call; no module in this engine calls a model provider's API directly. The model used for a run is whatever --model resolves to, left unset by default so omp's own configured default model answers — never a model name hardcoded in this engine.
  • 9Every agent's system prompt instructs it to answer in at most 120 words and to prefer a verified web search over an unverified claim when the claim is central to its argument. Independently of whether the model complies, the engine enforces a hard backstop: any turn's stored and displayed text is truncated to 200 words, and the turn is flagged truncated: true in storage when that backstop fires — the flag reports the backstop, not the model's own compliance with the 120-word instruction.
  • 10Every debate, question, and turn (speaker side, role, stage, model used, full text, citations extracted from URLs the turn's own text contains, start/end timestamps, the truncated flag) is persisted to a local SQLite database, so a debate survives the process exiting.
  • 11debate show <debate-id> prints the full persisted transcript for that debate, question by question, stages in the order they actually ran.
  • 12debate list prints every persisted debate with its topic, question count, and creation time.

Retrospective

What happened

  • Cycle 0 (build):T1–T6 built the whole engine (scaffolding/store, omp_client, agents, engine, cli+README, SKILL.md) with no reviewer or tester tasks in between — the plan went straight from six builders to feature-validate-lead with zero per-task review/mutation-proof gates in this cycle, unlike cycle 1. Every cycle-0 task also finished far faster than planned: T1 took ~2.5 real minutes against an expected_minutes of 25, T2 ~3.1 against 20, T3 ~3.1 against 20, T4 ~5.7 against 35, T5 ~4.8 against 25, T6 ~1.7 against 15 — actual wall time ran at roughly 10–25% of estimate on every single cycle-0 task, a one-directional estimation bias, not noise.
  • Cycle 1 (trigger — feature-validate-lead FAIL):5 of the 6 cycle-0 build tasks failed — only T6 (the SKILL.md doc task) passed clean. The findings were almost entirely test-coverage gaps caught by mutation testing — T1 (turn fields and DebateSummary.created_at never asserted by value), T2 (test_builds_argv_without_model_or_tools discarded its own return value), T4 (max_rebuttal_rounds only ever exercised at its default; no cross-call transcript-propagation assertion; no two-question-same-debate test), T5 (override test values indistinguishable from three different defaults at once; debate show fixture too thin to prove ordering) — plus one real production bug in T3: build_host_system_prompt never appended the Requirement 9 word-cap/verified-search instruction that the debater and judge prompt builders both carried, even though Requirement 9 explicitly names "every agent's system prompt" including the Host's question generation.
  • Cycle 1 added 15 tasks to close those five findings: T7–T11 (the fixes, expected_minutes 12+10+12+18+18 = 70) plus a dedicated reviewer and mutation-proof task per fix, R7–R11 and TE7–TE11 (5 × 5 = 25 minutes expected each, 50 total). All 15 ran in parallel lanes per fix and the whole batch — fixes, then review/mutation-proof — completed in about 11 real minutes (08:35:00 → 08:46:00) against 120 minutes of summed expected_minutes, i.e., heavy parallelization recovered most of the estimation slack cycle 0 already showed.
  • actual_tokens is null for every single task in the table, cycle 0 and cycle 1 alike (T1–T11 all show null in that column even where estimated_tokens was filled in, e.g. T1's 20900). estimated_tokens itself is also missing for T4, T5, and T6 in cycle 0 — the PM filled it for T1–T3 and every cycle-1 fix task but not for the three largest cycle-0 builders. Net effect: this plan cannot support any real token-cost analysis after the fact — every number in the "did this cost what we thought" question is either absent or itself an estimate.
  • UAT (U1) ran once, in cycle 1, and passed against the real omp CLI (REQ-1 through REQ-12 all checked, 22 real turns across 2 questions persisted and round-tripped correctly via direct DB query). Cycle 0's log records UAT: not_run — U1 was gated behind validate-lead's cycle-0 FAIL and only executed once the fix cycle's PASS cleared it, so the feature only ever ran UAT once, not once per cycle.

Proposals

  • Give cycle 0's own build tasks (T1–T6, or whichever tasks a future plan's first cycle contains) a reviewer + mutation-proof task immediately after each builder, the same shape cycle 1 used for T7–T11, instead of routing straight to feature-validate-lead. Four of the five cycle-1 findings were exactly the class of gap a per-task mutation-proof step is built to catch (assertions on discarded return values, parameters only ever exercised at their default, fixtures too thin to distinguish pass from fail); catching them at the task level would plausibly have avoided the second cycle entirely rather than deferring the same check to a later cross-cutting gate.
  • For any requirement whose wording implies a property must hold identically across multiple sibling builder functions — here, Requirement 9's "every agent's system prompt" across build_debater_system_prompt, build_judge_system_prompt, and build_host_system_prompt — write one parametrized test that iterates over all three builders and asserts the shared instruction text in each, rather than three independent per-builder tests. T3's bug was exactly a missing-in-one inconsistency across three sibling functions that per-function tests didn't structurally compare.
  • Require every task-table row to carry a real actual_tokens value before a task is marked complete, and require estimated_tokens on every builder task at plan time (T4/T5/T6 shipped without one). As written, this plan's token column is unusable for judging real cost against estimate on any task, cycle 0 or cycle 1.
  • Given that cycle-0 actual durations landed at roughly 10–25% of expected_minutes on all six tasks (not one outlier), recalibrate the estimator for this task shape (single-module builder task, Python, this repo) downward rather than treating each individual estimate as independent guesswork — the same bias recurred across every task in the cycle.
