debate is a Python CLI that runs structured, evidence-grounded debates between two AI teams. Give it a topic, and it builds a FOR team and an AGAINST team — three agents each (Lead, Researcher, Rebuttal) — then runs questions through a fixed pipeline: private research huddle, openings, a budgeted rebuttal loop, closings, and an optional judge verdict. Questions can be supplied by a human one at a time (debate ask) or generated by the engine itself in a batch (debate auto --count N).

Why it exists: to turn "ask one model a question" into a repeatable, adversarial, evidence-checked format — two sides forced to back claims with live web search, with every turn persisted so the result survives the process exiting and can be replayed later (debate show).

Why it's provider-agnostic by construction: every single agent turn — huddle, opening, rebuttal, closing, verdict, even the Host's question generation — is exactly one non-interactive subprocess call to the omp CLI. Nothing in this engine talks to a model provider's API directly, and nothing hardcodes a model name; --model is left unset by default so whatever omp is configured to use answers. omp's own web_search tool is how agents ground claims in real evidence, rather than this engine managing its own search API key.

What's deliberately not here: a Discord bot front-end. That's an explicit, named follow-up — this feature ships only the CLI and an omp skill that wraps it for LLM-driven callers.

The six sections below follow the dependency order the engine was actually built in: storage and config first, then the one place that's allowed to shell out, then the personas that script each agent, then the pipeline that sequences them, then the CLI surface, then the skill that lets an omp session drive it all.

Persistence and config

config.py · store.py

DebateConfig is a small dataclass holding the five knobs a debate run needs: topic, model, max_rebuttal_rounds (default 2), max_minutes (default 10), judge_enabled (default on). __post_init__ rejects an empty or whitespace-only topic immediately — the first line of defense against a silently-accepted blank topic.

Store is the SQLite layer and the only place debate/question/turn rows get written or read. It persists everything a turn carries: speaker side, role, stage, model used, full text, citations auto-extracted from URLs the turn's own text contains, start/end timestamps, and the truncated flag — so a debate survives the process exiting and debate show/ debate list have something durable to read back. Default DB path is ~/.debate/debate.db, overridable globally via --db-path.

The omp subprocess client

omp_client.py

This is the layering boundary the whole feature is built around: the only module in src/debate allowed to import subprocess or use asyncio.create_subprocess_exec. A grep/AST scan across every other .py file under src/debate/ enforces that nothing else shells out to omp on its own — the thing that would quietly defeat the provider-agnostic guarantee.

run_omp_turn builds and awaits exactly one omp -p --mode text call per agent turn. Since omp -p takes a single prompt argument rather than separate system/user flags, the client combines them into one string with labelled [System instructions] / [Task] blocks — legible in captured transcripts without inventing chat-style markup omp -p doesn't understand.

It also owns the hard backstop: independent of whether the model honors its own 120-word instruction, every returned turn is counted and truncated to 200 words if it runs over, with truncated: True flagged on the result. This is a blind backstop — it only ever fires at the 200-word line, regardless of the model's own compliance.

Agent personas

agents.py

Pure prompt-building, no process spawning. One function builds all six debater personas — build_debater_system_prompt(side, role, topic) for every (FOR/AGAINST) × (Lead/Researcher/Rebuttal) combination — plus build_judge_system_prompt(topic) for the out-of-team Judge and build_host_system_prompt(topic, already_asked) for the question-generating Host used by debate auto.

Every persona's prompt carries the same two shared instructions: a 120-word answer cap, and a preference for a verified web search over an unverified claim when the claim is central to the argument. The Host persona additionally receives the full list of questions already asked in the debate, so it can avoid ever repeating one.

The pipeline engine

engine.py

This is where the question-pipeline stage order is encoded exactly:

  1. Huddle (private, per team) — each team's Researcher produces an evidence brief with --tools=web_search enabled; the brief is folded into every later prompt to that team's Lead and Rebuttal for this question.
  2. Openings — FOR's Lead, then AGAINST's Lead.
  3. Rebuttal loop — AGAINST's Rebuttal speaks first, then FOR's, alternating, bounded by whichever of two limits is hit first: max_rebuttal_rounds * 2 turns, or a max_minutes wall-clock deadline computed once when the loop starts and checked only before a new turn begins — a turn already in flight is always allowed to finish.
  4. Closings — AGAINST's Lead, then FOR's Lead, so FOR holds both the opening and the closing word.
  5. Verdict — one Judge turn (web-search enabled) if the judge is enabled, naming a winner or declared draw with a rationale citing specific turns by stage and side; skipped entirely if --no-judge.

Every stage's prior turns reach later prompts via a transcript renderer, so a rebuttal is actually responding to what was said earlier, not just to the topic in isolation. The same module's generate_next_question() implements the Host-mode path for debate auto, reading the debate's own question history back from the store so the Host agent never repeats a question.

The CLI

cli.py

Five subcommands, thin wrappers over config/store/engine:

  • debate start --topic "<text>" — creates a debate (rejecting a blank/whitespace topic), storing --model / --max-rebuttal-rounds / --max-minutes / --no-judge as that debate's defaults; prints the new debate id.
  • debate ask "<question>" — runs one question through the full pipeline on the target debate. Flags here override the debate's stored defaults for that single call only, never mutating the stored row.
  • debate auto --count N — runs N consecutive Host-generated questions with no human supplying any of them, printing each question and result as it completes.
  • debate show <debate-id> — prints the full transcript, question by question, in the exact order stages actually ran.
  • debate list — prints every persisted debate with topic, question count, and creation time.

All five accept a global --db-path for pointing at a non-default SQLite file. "Active debate" (used when --debate-id is omitted on ask/auto) resolves to the most recently created debate — documented as safe only immediately after a start in the same session.

The omp skill

.claude/skills/debate/SKILL.md

Documents the CLI for an omp session to drive directly, plus a second way to run multiple questions that the CLI alone doesn't give you: instead of delegating question choice to the engine's Host agent via debate auto, the orchestrating session can compose each next question itself — using its own judgment and debate show's transcript — and pass it straight to debate ask, skipping the Host agent's extra omp call entirely. The skill is explicit that --debate-id should always be passed rather than relying on the "most recent debate" fallback, and restates the Discord-is-future-work boundary.
